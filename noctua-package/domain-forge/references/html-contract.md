# The domain-forge HTML contract — v3

The output is ONE self-contained `.html` file, no network deps. The file is for **AI agents and humans**: it must be navigable as a tree without parsing DOM, and any individual component must be swappable without breaking the whole.

**How to read this document.** The primary reader is the **apply phase** — the orchestrator's main conversation, which reads this once before editing the output HTML. If that's you, three sections carry what you need: **Architecture in one sentence** (the canonical model), **The canonical data blocks** (the schemas you edit), and **Practical instructions for the apply phase** (the steps, at the very end). The **Composition layout** section immediately below and **Engine modularity** further down are optional/advanced — they serve downstream codegen and engine-swap tooling, not a normal apply. Skim or skip them on a first read.

## Composition layout — optional, advanced (sub-HTML source files → composed model)

A domain-forge model can be authored as a **source folder of per-entity HTML fragments** that the composer assembles into the single deliverable HTML. This is the supported model for codegen-ready, edit-one-file-redeploy workflows.

There are two authoring paths, and they are two views of the **same** artifact, not rival formats:

- **Direct** — edit the three canonical `<script>` blocks of a single composed file in place (see **Architecture in one sentence** below, and the apply-phase steps at the end of this document). This is the minimal path the orchestrator's apply phase uses.
- **Source-folder** — the expanded view in this section: author one fragment per entity/relationship, then `scripts/compose_model.py` assembles them. Better for codegen and one-file-at-a-time edits.

`scripts/compose_model.py` and `scripts/explode_model.py` convert losslessly between the two. **Either way, the composed file's three script blocks are the source of truth** — everything else is generated from them.

```
<source>/
├── model.meta.json            # base IRI, prefixes, @context, codegenTargets, components, model-level designRationale
├── overview.md                # prose summary (rendered in Ontology > Overview)
├── entities/
│   └── <component>/           # one subdirectory per bounded context — maps to a codegen package
│       └── <Name>.html        # one self-contained, browsable HTML fragment per class / value object / individual
├── relationships/
│   └── <component>/
│       └── <name>.html        # one fragment per object / data property; declares domain → range
├── logic/                     # optional
│   ├── dmn.json
│   ├── horn.pl
│   └── swrl.json
└── index.json                 # GENERATED by composer: IRI → source-file map + codegen hints
```

Each entity / relationship fragment is its own standalone HTML, viewable in a browser, with two required script blocks:

```html
<script type="application/x-df-entity-data" id="entity-data">{ ...JSON-LD node for this element... }</script>
<script type="application/x-df-entity-ttl"  id="entity-ttl"> ...Turtle for this element... </script>
```

The JSON-LD node carries the standard fields (`@id`, `@type`, `domain`, `range`, `component`, `valueObject`, `label`, `comment`, `subClassOf`, `equivalentClass`, …) PLUS:

- `designRationale: { choice, alternatives[], tradeoffs, anchors[] }` — *why* this modelling choice. Rendered as a colored block on the entity card and inside the details panel. Hinkelmann M1 slide 11: "reading the report is entirely sufficient to understand the solution and the reasoning behind it."
- `codegen: { kind, identity?, mutable?, java?, typescript?, sql?, python?, ... }` — per-target-language hints so a downstream codegen tool can dispatch on `codegen.kind` and emit a class / interface / table / dataclass. Examples:
  - On a class: `"codegen": {"kind": "entity", "identity": "sku", "java": {"className": "Product", "package": "catalog"}, "sql": {"tableName": "products"}}`
  - On a value object: `"codegen": {"kind": "value-object", "immutable": true, "java": {"useRecord": true}, "python": {"useDataclass": "frozen"}}`
  - On an object property: `"codegen": {"kind": "composition" | "cross-context-reference" | "value-association", "cardinality": "1..*", "owningSide": "Order", "java": {"fieldName": "lineItems", "fieldType": "List<LineItem>"}}`
  - For cross-context references (e.g., `refersToProduct`): the SQL hint is `"noForeignKey": "cross-context"` — the relation lives by id, not by FK, which is exactly what DDD-AntiCorruption requires.

### Composition workflow

```
# author / agent edits one file
$ vim source/entities/billing/Money.html

# re-compose
$ python3 scripts/compose_model.py source/ --out model.html
composed 4 entities + 3 relationships → model.html (220,000 bytes)
  index: source/index.json

# validate
$ python3 scripts/validate_model.py model.html
9 passed, 0 failed
```

The composer regenerates `index.json` on every run. A codegen tool then walks `index.json` (not the HTML fragments) — it has direct IRI → source-file + codegen-hint lookups:

```json
{
  "base": "http://example.org/shop#",
  "codegenTargets": { "java": {...}, "typescript": {...}, "sql": {...}, "python": {...} },
  "components": { "catalog": {...rationale...}, "billing": {...rationale...} },
  "entities":     [ {"iri":"ex:Product","source":"catalog/Product.html","component":"catalog","codegen":{...}}, ... ],
  "relationships":[ {"iri":"ex:hasLineItem","source":"billing/hasLineItem.html","codegen":{...}}, ... ]
}
```

### Why the per-component subdirectories matter

Each component subdirectory under `entities/` and `relationships/` maps directly to a **target-language package** (Java `com.example.shop.catalog`, Python `shop.catalog`, TypeScript `src/catalog/`, SQL `catalog` schema). Codegen walks `entities/catalog/*.html` and emits one output file per source file into the `catalog` package. The DDD bounded-context boundary is preserved in the filesystem layout, which is preserved in the codegen output.

The reverse split is also supported: `scripts/explode_model.py` takes a composed HTML and writes back the source folder structure — useful when starting from an existing model.

## Architecture in one sentence

> Three `<script>` blocks at the top of the file are the **canonical data**; the entire visible body is rendered from them at page load by the inline runtime.

That's the composability contract. To swap a class, an agent edits the triples inside `<script id="domain-model">` and `<script id="model-jsonld">` (and the matching paragraph in `<script id="model-markdown">` if affected) — nothing else. On next load, the diagram, ontology browse, syntax pane, summary, and logic pane all re-render to match.

## The canonical data blocks — three required, three optional

1. **Turtle — the source of truth.**
   ```html
   <script id="domain-model" type="text/turtle">
   @prefix ex: <http://example.org/shop#> .
   @prefix owl: <http://www.w3.org/2002/07/owl#> .
   @prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
   @prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

   ex:Account a owl:Class ; ex:component "billing" .
   ex:Money   a owl:Class ; ex:component "billing" ; ex:valueObject "true" .
   ex:owns        a owl:ObjectProperty   ; rdfs:domain ex:Person ; rdfs:range ex:Account .
   ex:hasBalance  a owl:DatatypeProperty ; rdfs:domain ex:Account ; rdfs:range xsd:decimal .
   </script>
   ```
   - Every class **must** carry `ex:component "<group>"`. The component is the addressable subcomponent.
   - Value objects are marked with `ex:valueObject "true"`.
   - Every object property declares `rdfs:domain` and `rdfs:range`, both referencing declared `owl:Class` IRIs.
   - Every data property declares `rdfs:domain` (a class) and `rdfs:range` (an `xsd:` datatype).

2. **JSON-LD — both-ways mirror.** The same model expressed as JSON-LD `@graph`. The runtime parses this to drive every view, so it is the operational source. **Keep it in sync with the Turtle** — every class IRI in one must appear in the other. **Precedence:** when they conflict, the Turtle wins — it is the canonical source of truth and the JSON-LD is the operational mirror the runtime renders. Nothing auto-syncs them in the direct-edit path (you hand-edit both), so if they diverge, treat the Turtle as authoritative and regenerate the JSON-LD to match.

   **OWL/RDFS feature schema per node** — used by the Hierarchy view, the entity cards, Manchester / RDFS projections, and the new Protégé-style displays:

   On a class node (`"@type": "owl:Class"`):
   - `subClassOf`: array of class IRIs — `rdfs:subClassOf`. Drives the class tree.
   - `equivalentClass`: array — `owl:equivalentClass` (shown as `≡` chips).
   - `disjointWith`: array — `owl:disjointWith` (shown as `⊥` chips).
   - `restrictions`: array of `{ onProperty, type, value }` where `type` is one of `someValuesFrom`, `allValuesFrom`, `hasValue`, `cardinality`, `minCardinality`, `maxCardinality`.
   - `label` / `comment`: strings — `rdfs:label` / `rdfs:comment`. Shown in annotations block.

   On a property node (`"@type": "owl:ObjectProperty"` or `"owl:DatatypeProperty"`):
   - `characteristics`: array picked from `["Functional", "InverseFunctional", "Transitive", "Symmetric", "Asymmetric", "Reflexive", "Irreflexive"]`. Render as colored OWL badges. Alternative: also typed via `"@type": ["owl:ObjectProperty", "owl:TransitiveProperty"]`.
   - `subPropertyOf`: array of property IRIs — `rdfs:subPropertyOf`. Drives the property tree.
   - `inverseOf`: property IRI — `owl:inverseOf` (only on object properties).
   - `label` / `comment`: as above.

   ```html
   <script id="model-jsonld" type="application/ld+json">
   { "@context": { ... }, "@graph": [
       {"@id": "ex:Account", "@type": "owl:Class", "component": "billing"},
       {"@id": "ex:owns",    "@type": "owl:ObjectProperty",
        "domain": "ex:Person", "range": "ex:Account"}
   ] }
   </script>
   ```

3. **Markdown — the human description (the page headline).** Plain Markdown rendered as the always-visible **Abstract** at the top of the document — the first thing read, above the diagram and tabs. Make it a **detailed textual description of the domain model**, not a terse summary: several short paragraphs (~15–30 lines, longer when warranted) covering purpose & scope, each component, the load-bearing modeling decisions and *why*, which knowledge layers are used and the expressivity limit behind each choice, and the open questions. Standard to hit: reading this alone should be enough to understand the model and its reasoning.

   ```html
   <script id="model-markdown" type="text/markdown">
   # Model name
   - **component-a** — short description …
   - **component-b** — …
   ## Open
   - …
   </script>
   ```

4. *(Optional)* **DMN content** in `<script id="model-dmn" type="application/json">`. Validated when non-empty (invariant 10). Schema:

   ```json
   {
     "decisions": [
       {
         "id":        "ex:RiskScore",        // IRI for the decision
         "hitPolicy": "U",                   // U|A|P|F|C|R|O (+ C+|C<|C>|C# for collect variants)
         "inputs":    ["Transaction.hasAmount"], // "Entity.dataProperty" form; resolves against the ontology
         "outputs":   ["riskPoints"],
         "rules": [
           {"inputs": ["[10000..]"],    "output": 90},
           {"inputs": ["[1000..10000)"],"output": 30},
           {"inputs": ["[0..1000)"],    "output": 0}
         ]
       }
     ]
   }
   ```

   Each rule must have **exactly as many input cells as `inputs` declares columns**. Each cell is a **FEEL expression** — one of:
   - `-` (irrelevant / don't-care)
   - a literal: `"Italy"`, `42`, `-1.5`, `true`, `false`, `null`
   - a comparison: `>10000`, `<=1000`, `=42`, `!=0`
   - an interval (math bracket notation): `[1000..10000]` (closed), `[0..1000)` (half-open), `(100..200]` (lower-exclusive)
   - a negation: `not("Italy")`

   The validator flags any cell that doesn't match one of those forms. Inputs written as `Entity.property` are checked against the ontology — undeclared classes or data properties are reported.

   **Make the DMN *runnable*, not just readable — the executable `drd` graph.** A bare
   `decisions` array lists tables but says nothing about how they chain, so the page can
   render them but not *run* a transaction end-to-end. Add an **optional `drd` object**
   (a sibling of `decisions`) that wires the Decision Requirements Diagram into something
   the embedded DMN runtime can execute. This is what lets the composed file ship a
   working **Test** tab where a reader enters inputs and watches the model compute the
   outcome with a per-step trace. It is purely additive: the validator ignores `drd`
   (invariant 10 still checks only `decisions`, which stay **tables-only**), and a model
   with no `drd` falls back to per-table evaluation.

   ```json
   {
     "decisions": [ /* ...rule tables only, incl. any BKM table; each carries `outputs:[<label>]`... */ ],
     "drd": {
       "inputData": [
         {"name": "Merchant Country", "type": "string", "default": "South Africa"},
         {"name": "Payment Amount",   "type": "number", "default": 11234}
       ],
       "nodes": [
         {"id":"ex:MerchantContinent","name":"Merchant Continent","kind":"invocation",
          "invokes":"ex:ContinentOfCountry","bindings":{"Country":"Merchant Country"},
          "output":"Merchant Continent"},
         {"id":"ex:TotalRiskScore","name":"Total Risk Score","kind":"expression",
          "op":"sum","operands":["Location Risk Score","Residence Risk Score",
          "Amount Risk Score","Special Combination Risk Score"],"output":"Total Risk Score"}
       ],
       "final": "ex:TransactionOutcome",
       "knowledgeSources": [ {"id":"ex:BankFraudRiskPolicy","name":"Bank Fraud-Risk Policy"} ],
       "authorities": [ {"from":"ex:BankFraudRiskPolicy",
          "to":["ex:LocationRiskScore","ex:ResidenceRiskScore","ex:AmountRiskScore","ex:SpecialCombinationRiskScore"]} ],
       "scenarios": [
         {"label":"Mensoni","inputs":{"Merchant Country":"South Africa",
          "Cardholder Residence Country":"Italy","Payment Amount":11234}}
       ]
     }
   }
   ```

   A BKM is just a decision in `decisions` carrying `"kind":"businessKnowledgeModel"`; it is
   drawn as a clipped-corner node and reached only through the dashed knowledge requirement
   of the `invocation` node(s) that call it (so one BKM, invoked twice, appears once and fans
   out — DRY made visible). `knowledgeSources` are governing authorities (the bank's prose
   policy, an external system) and `authorities` are the dashed circle-headed edges from a
   source to the decisions it governs. These two fields are what let the **Logic tab's
   diagram** be a *complete* Decision Requirements Diagram — input data, decisions, BKMs, knowledge sources,
   and all three requirement edge kinds — rather than a bare box-and-line sketch. Emit them
   from the same Turtle wiring the extractor records (`knowledgeSource` annotations become
   `authorities`; the `KnowledgeSource` individuals become `knowledgeSources`).

   Everything is wired **by label**: a table's `outputs[0]` is the value it produces; an
   `invocation` node runs a (BKM) table from `decisions` with `bindings` mapping the
   table's parameters to source labels, and republishes the result under `output` (this
   is how *one* BKM is invoked twice under two different output labels — DRY); an
   `expression` node combines other labels (`op`: `sum`|`max`|`min`). `inputData` are the
   leaves the user supplies; `final` is the sink decision shown as the headline result;
   `scenarios` become one-click prefill buttons (ideal for the acceptance cases **and**
   the edge cases that probe a model's open questions — e.g. a negative amount that
   matches no band shows up as an unscored gap). The runtime resolves the graph to a
   fixpoint, so node order in the JSON does not matter. A table that is only ever invoked
   (a BKM) is not auto-run as a top-level table — it fires solely through its invocation.

   **Apply-phase guidance.** When you populate the `dmn` layer and the decisions form a
   multi-step DRD (sub-decisions, a BKM, a summation), emit the `drd` graph too — it is
   the difference between a diagram of the logic and a model the reader can actually
   execute. The extractor already records the DRD wiring (the `requires` / `invokes` /
   `feelExpression` annotations on the Decision/BKM individuals in the Turtle); translate
   that wiring into `drd.nodes` + `drd.final`, lift the input-data leaves into
   `drd.inputData`, and turn the acceptance scenarios into `drd.scenarios`. (The full
   apply-phase guidance for DMN and the knowledge graph is the section *Apply-phase
   guidance: runnable DMN and knowledge-graph layers* below.)

   **DMN source export.** The runtime's DMN-XML projector only serialises the `decisions`
   tables; to ship a *complete* DMN 1.5 DRG (the BKM as a `businessKnowledgeModel`, the
   invocations with `knowledgeRequirement`, the boxed total as a `literalExpression`, the
   `knowledgeSource` with `authorityRequirement`, and decision-to-decision
   `informationRequirement`s), run `scripts/dmn_drg.py <model.html> --out model.dmn` — it
   builds the full DRG from the `drd` graph. Embed that XML verbatim in a
   `<script id="model-dmn-xml" type="application/xml">` block: the `dmnxmlSrc()` projector
   **prefers an embedded `#model-dmn-xml`** when present, so the Syntax tab's *DMN XML* view
   shows exactly the on-disk `.dmn`. Note FEEL output rendering: numeric outputs print bare
   (`60`), string outputs print as FEEL string literals (`"Europe"`), per the standard.

5. *(Optional)* **SWRL rules** in `<script id="model-swrl" type="application/json">` — Protégé-compatible. Each rule is `{ id, label, comment, antecedent[], consequent[] }`. Each atom is one of:

   | Atom type | Shape | Renders as |
   |---|---|---|
   | `class` | `{"type":"class","class":"ex:Person","args":["?x"]}` | `Person(?x)` |
   | `objectProperty` | `{"type":"objectProperty","property":"ex:hasParent","args":["?x","?y"]}` | `hasParent(?x, ?y)` |
   | `dataProperty` | `{"type":"dataProperty","property":"ex:hasAge","args":["?x", 18]}` | `hasAge(?x, 18)` |
   | `builtin` | `{"type":"builtin","builtin":"swrlb:greaterThanOrEqual","args":["?n", 18]}` | `swrlb:greaterThanOrEqual(?n, 18)` |
   | `sameAs` | `{"type":"sameAs","args":["?x","?y"]}` | `sameAs(?x, ?y)` |
   | `differentFrom` | `{"type":"differentFrom","args":["?x","?y"]}` | `differentFrom(?x, ?y)` |

   The Logic tab renders each rule as `antecedent ⟹ consequent` with one atom per line, colour-coded by atom type. The Syntax tab exposes a SWRL presentation-syntax projection.

6. *(Optional)* **Horn clauses** in `<script id="model-horn" type="text/plain">`. Validated when non-empty (invariant 11). One clause per line, terminating with a period:

   ```prolog
   % Fact form
   transaction(tx_042).
   has_amount(tx_042, 11234).

   % Rule form: head if body
   high_value(T) :- transaction(T), has_amount(T, A), A >= 10000.
   ```

   Conventions enforced by the validator:
   - **Class predicates have arity 1** — `transaction(T)`, not `transaction(T, X)`.
   - **Object and data properties have arity 2** — `has_amount(T, A)`, `owns(P, A)`.
   - Every predicate in a clause body must resolve to one of: an ontology term (class / object / data property, matched by lowercased local name), a Prolog built-in (`=`, `<`, `>=`, `is`, `not`, `member`, …), or a derived head defined elsewhere in this block.
   - Lines starting with `%` are comments and ignored.

   A malformed clause, an undeclared predicate, or an arity mismatch fails invariant 11.

## What the runtime renders

| Tab | Source | What it shows |
|---|---|---|
| **Diagram** (default) | JSON-LD `@graph` | SVG: per-component clusters, layered layout, clickable/draggable nodes, search, zoom, component filters. **When the model carries individuals (an A-box), it becomes the unified course-style knowledge graph (KE-07): blue class *ellipses* and yellow individual *ellipses* in the same canvas, framed into a blue **Schema (T-box)** region over an orange **Individuals / Data (A-box)** region, joined by blue `rdf:type` edges; `subClassOf` is red. Three layer chips (`#diagram-layers`: Classes / Individuals / Inferred) and a `#diagram-reason` button appear; pressing it overlays the reasoner's inferences (inferred memberships, derived properties, classifications) onto the graph. A pure-T-box model (no individuals) keeps the classic class diagram and hides the chips/button.** See "The unified knowledge-graph diagram" below. |
| **Ontology** | JSON-LD `@graph` | Browsable structured catalog — per-component cards, each class with its data props and relationships. |
| **Logic** | `model-dmn` (+ `drd`) + `model-horn` + SPARQL + `model-swrl` | **SPARQL view** carries an **in-browser SPARQL runner** (`.kg-runner`, from `@KG_RUNTIME`) above the static example cards: pick/edit a SELECT query, Run it against the model's triples, toggle asserted ↔ asserted+inferred. **SWRL view** (when `model-swrl` has rules) carries an **on-demand reasoner runner** — a "⚛ Run reasoner" button that lists the inferred triples grouped by kind (class memberships / subclass entailments / derived properties) with provenance. Both gated: they mount only when their view + content exist. When `model-dmn` has decisions, the DMN view is organised (by the `@DMN_TESTER` workspace block) into three sub-views: **Diagram** — the complete Decision Requirements Diagram (`buildCompleteDrd`): input data (stadium), decisions (rectangle), BKMs (clipped-corner, reached by a dashed knowledge requirement from their invocation), knowledge sources (wavy, dashed authority edges), layered by dependency depth and coordinate-aligned so chains form near-vertical columns, **every box draggable** (edges re-route live); **Test** — an interactive runtime that resolves an input end-to-end (invocations, Hit-Policy-U tables, `sum`/`min`/`max` expressions) to the `final` decision with a per-step trace and `drd.scenarios` prefills; **Rules** — every decision-logic element one at a time via a submenu (no long scroll): the decision tables, plus the boxed **FEEL expression(s)** (e.g. the total) and the **knowledge source(s)** rendered as description cards. Clicking a Diagram node **or** a Test trace row opens a **side panel** (drawer) showing that decision's full rule table (`window.__dfShowTable`) — no tab switch; **Rules** remains for browsing all tables. Without a `drd`, Diagram falls back to the legacy decisions-only figure and Test to per-table evaluation. The restructure touches only the DMN view, so Horn rules and SPARQL examples (other views) are unaffected; no DMN → none of this appears. |
| **Syntax** | All of the above | **Turtle · RDFS · JSON-LD · Manchester · N-Triples · RDF/XML · DL · Prolog · Datalog · SPARQL · SWRL · DMN XML · Markdown** — thirteen serialisations, syntax-highlighted, with Copy and Download on the active tab. Everything except Turtle, JSON-LD, the Markdown summary, and the canonical `model-dmn` / `model-horn` / `model-swrl` JSON is a **derived projection** computed by the runtime — you do not write them. **DMN XML** is DMN 1.5 and downloads as `model.dmn`; drag it into Camunda Modeler or Trisotech to edit the decision tables in a graphical modeller. |
| **Summary** | `model-markdown` | Rendered Markdown (headings, lists, bold/italic, code, links). A "View source" toggle exposes the raw Markdown. |

The details panel (slide-out on click) shows the clicked element's properties, in/out relationships, and a small Turtle snippet scoped to that element. The "Open full Syntax →" link jumps to the Syntax tab.

## The unified knowledge-graph diagram (KE-07 convention)

When the model has an A-box (`individuals()` non-empty), the Diagram tab renders one graph holding both levels, in the convention of the course slides (KE-07 "Schema vs. Instances/Data"):

- **Nodes are ellipses.** Classes are blue ellipses (`buildNode`); individuals are yellow ellipses (`buildIndNode`). Each individual node carries `data-iri`, `data-c="entity"`, `data-component`, so search / focus / drag / component-filter work on it like any class node. Datatype properties are not drawn inside the node — they appear in the click-to-inspect panel.
- **Edges are coloured by kind** (`drawEdge` adds the kind as a class): `subClassOf` = **red** (`.edge.subclass`), `rdf:type` = **blue** (`.edge.type`, routed vertically between the bands), object properties = dark (`.edge.object` / `.edge.abox`). Repeated A-box relation labels are de-duplicated.
- **Two framed regions** (`.level-frame.schema` / `.level-frame.data`, labelled "Schema (T-box)" / "Individuals / Data (A-box)") wrap the class band over the individual band. The A-box is laid out in instance-flow columns, barycenter-ordered to minimise crossings (`orderComponents` + the A-box band in `layoutAll`).
- **Layer chips** `#diagram-layers button[data-layer="classes|individuals|inferred"]` toggle `svg#diagram.hide-classes` / `.hide-individuals` / `.reasoned`. The **`#diagram-reason`** button runs the reasoner and reveals the `.inf` overlay (inferred `rdf:type` edges + per-individual tags). Both controls are hidden (`hidden` attribute toggled in `drawDiagram`) when there are no individuals.
- The inference overlay reads `window.__kg.triples(true)` defensively (`aboxInferred`), so the diagram still renders if the `@KG_RUNTIME` block is absent.

## In-browser SPARQL + reasoner runtimes (`@KG_RUNTIME`)

An additive, reversible block delimited by `<!-- @KG_RUNTIME:start -->` … `<!-- @KG_RUNTIME:end -->` (a `#kg-runtime-style` + `#kg-runtime` pair, placed before `</body>`). It depends on the main runtime exposing **`window.__kgReasoning = getReasoning`** and itself exposes:

```
window.__kg = { runSparql(text) → {vars, rows}, triples(withInferred) → [{s,p,o|v,lit,inferred,prov}], setReasoned(on), state }
```

It self-mounts two `.kg-runner` panels (both self-gating — they return false if their view/cards are absent, and retry until the Logic views render):

- **SPARQL runner** into `[data-logic-view="sparql"]` — a small in-browser SELECT engine: BGP with `; , .` shorthand, the `a` keyword, prefixed IRIs, DISTINCT. **No** OPTIONAL / FILTER / aggregation / property paths. Example-query chips are seeded from the static `.sparql-q` cards; the PREFIX block is shown once in a collapsible note and the textarea autosizes.
- **Reasoner runner** into `[data-logic-view="swrl"]` — the "⚛ Run reasoner" button + grouped inferred-triple list with provenance.

`setReasoned(true)` flips the asserted↔inferred view and broadcasts to subscribers (the diagram overlay and the SPARQL runner state badge). The reasoner itself is the existing engine (`@ENGINE_BLOCK` / `runReasoner`), consulted lazily through `triples()`.

## Apply-phase guidance: runnable DMN and knowledge-graph layers

**DMN.** make the model **runnable and completely drawn**, not just a set of tables. Whenever `model-dmn` has decisions, the **Logic tab** is reorganised into three sub-views — **Diagram · Test · Rules** — so the picture, the tester and the rules live together (no back-and-forth between top-level tabs): *Diagram* is the complete, layered, draggable DRD (`buildCompleteDrd`: input data, decisions, **BKMs** reached by a dashed knowledge requirement from their invocation, knowledge sources with dashed authority edges, all three requirement edge kinds); *Test* runs an input end-to-end with a per-step trace; *Rules* lists the decision tables one at a time via a submenu (so a long model doesn't become an endless scroll). Clicking a node on the Diagram **or** a row in the Test trace opens a **side panel** with that decision's full rule table (`window.__dfShowTable`) — the rule behind any step is one click away, without leaving the diagram or the trace. All of this is driven by the optional `drd` graph you emit alongside `decisions`: input-data leaves, invocation/expression nodes, the `final` decision, the `knowledgeSources` and `authorities`, and the acceptance/edge `scenarios`. Translate it from the DRD wiring the extractor records in the Turtle (`requires` / `invokes` / `feelExpression` / `knowledgeSource` annotations and the `KnowledgeSource` individuals). See the `model-dmn` schema and the Logic-tab row above for the exact shape. It is purely additive and validator-safe — `decisions` stays tables-only, so invariant 10 is unaffected; a model with no DMN gets none of this; and the restructure only touches the DMN view, leaving Horn/SWRL/SPARQL views intact. Without a `drd` the Diagram falls back to the legacy decisions-only figure and Test to per-table evaluation, so a multi-step decision is worth the `drd`.

**Knowledge graph.** The **knowledge-graph layer is similarly runnable, and gated on content**. When the model carries **individuals (an A-box)**, the Diagram tab becomes the unified course-style knowledge graph (KE-07): blue class *ellipses* and yellow individual *ellipses* in one canvas, framed into a **Schema (T-box)** region over an **Individuals / Data (A-box)** region, joined by blue `rdf:type` edges (`subClassOf` red); layer chips (Classes / Individuals / Inferred) and a **Run reasoner** button appear, and running it overlays the reasoner's inferences. In parallel the **Logic → SPARQL** view gains an **in-browser SPARQL runner** (run `SELECT` over asserted-or-inferred triples) and, when `model-swrl` has rules, **Logic → SWRL** gains an **on-demand reasoner runner** (the inferred triples grouped with provenance). All of this is gated: a pure-T-box model with no individuals/SWRL shows the classic class diagram and static SPARQL example cards, and the KG controls stay hidden. Because of this payoff, **emitting a handful of representative A-box individuals per key class is high-value** whenever the domain offers concrete examples — it is what lights up the unified diagram, the SPARQL runner, and the reasoner overlay. Validator invariants 17–19 check these structures are present and functioning when the layer warrants them; see "The unified knowledge-graph diagram" and "In-browser SPARQL + reasoner runtimes" above.

## Engine modularity — the runtime is decomposable too

The inference engine — the reasoner that produces R.facts.inferred,
R.classSupers (inferred), and R.contradictions — lives in the inline runtime
`<script>` of every composed `model.html`, between the markers:

```js
/* @ENGINE_BLOCK_START — ... */
... initReasonerState + seedAssertedFacts + runReasoner ...
... inferSubClassClosure ...
... inferClassMembershipInheritance ...
... inferSubPropertyClosure ...
... inferPropertyCharacteristics ...
... inferSWRL (+ matchAntecedent + matchAtom + unify) ...
... detectContradictions ...
/* @ENGINE_BLOCK_END */
```

The source for these functions lives under
`assets/engine-source/capabilities/<id>/logic.js` — one capability per
folder. `scripts/compose_engine.py` reassembles them; `scripts/explode_engine.py`
goes the other direction (given a model.html, extracts the engine back to
source). Each capability also ships a standalone runnable `viewer.html`
that opens in any browser and lets you exercise just that capability
against an editable KB.

The engine block is byte-replaceable: a downstream tool can substitute it
to swap the reasoner without touching the data scripts. The validator
invariant 12 (projector round-trip through rdflib) catches engine
regressions automatically.

**Other reversible marker blocks** carried before `</body>`, each a self-mounting,
self-gating IIFE: `@DMN_TESTER` (DMN diagram/test/rules workspace), `@PROLOG_RUNNER`
+ `@PROLOG_WORKSPACE` (in-browser Horn/Prolog query engine + workspace, gated on
`#model-horn`), and `@KG_RUNTIME` (the in-browser SPARQL + on-demand reasoner runners,
gated on the sparql/swrl Logic views; see above). The main runtime must keep exposing
`window.__kgReasoning` for `@KG_RUNTIME` and the diagram overlay to work — validator
invariant 17 enforces this whenever the model has an A-box or SWRL.

## Layers — what a chain skill or a forge may append

Everything above describes the **base model**. Downstream skills (`/model-chat`, `/inferred-questions`) and the sibling forge `/dataset-forge` append **layers**: `<!-- @LAYER:start NAME -->` … `<!-- @LAYER:end NAME -->` blocks before `</body>`, each with a `layer-NAME-data` script, a `layer-NAME-render` script, an optional style, and a header stamped with the SHA-256 of the canonical Turtle it was produced against. The contract, the four validator invariants (13–16) and the platform scripts that write, strip, re-stamp and verify layers (`scripts/apply_layer.py`, `scripts/strip_layer.py`, `scripts/validate_model.py`) are in `references/future-skills.md`. Two consequences for the apply phase here: **never edit a layered file in place** (SKILL.md Step 2, *Layered input*), and never touch a `layer-*` block from the base runtime — the runtime and the layers are independent by contract.

## Composability — replaceable units

Each replaceable unit carries `data-c="<role>"` so a downstream agent can find and replace it cleanly:

- `data-c="model-root"` — the `<body>`
- `data-c="topbar"` / `tab-nav` / `meta`
- `data-c="diagram-pane"` / `ontology-pane` / `logic-pane` / `syntax-pane` / `summary-pane`
- `data-c="diagram"` (the SVG container)
- Within SVG: `data-c="entity"` (a `<g class="node">` with `data-iri`) and `data-c="relationship"` (a `<g class="edge">` with `data-prop`)
- Within the Ontology tab: `data-c="ontology-component"` (one per component) and `data-c="entity"` (one per class)
- Within the Logic tab: `data-c="dmn-decision"`, `data-c="horn-rules"`, `data-c="sparql-examples"`, `data-c="sparql-runner"` (the in-browser SPARQL runner), `data-c="reasoner-runner"` (the on-demand reasoner runner)

**But the supported, durable swap mechanism is editing the three data scripts.** The rendered DOM is regenerated on load; in-place DOM edits to rendered elements will be lost the next time the page opens. Edit data → see the change.

## What's removed in v3 (so you don't repeat it)

- No DOM mirror of entities/relationships outside the SVG. (The SVG is itself rendered from data.)
- No model-index aside. The Ontology tab replaces it.
- No top-of-page export toolbar. Copy and download live only in the Syntax tab, where the content actually is.
- No per-element syntax language switcher in the details panel — the Syntax tab is the place for that. The details panel shows a single Turtle snippet plus a jump link.

## Practical instructions for the apply phase (the orchestrator)

These steps belong to the **apply phase**, which runs in the orchestrator's main conversation — not in the read-only `domain-extractor` subagent. The extractor produces `model.ttl`, `blueprint.md`, and `findings.json` in the run directory and never touches any `.html`; the orchestrator materializes those artifacts into the HTML here.

1. Start from `assets/template.html` and **only edit the data `<script>` blocks** — the three required ones, plus `model-dmn`, `model-horn`, `model-swrl` when those layers are populated. Leave the rest of the file alone.
2. Fill Turtle and JSON-LD with the same set of classes / properties / individuals from the extractor's `model.ttl`; they must agree.
3. Fill the `model-markdown` block per the **Markdown — the human description** spec (block 3 above), drawing the prose from the extractor's blueprint (`§1`/`§2`/`§5`/`§6`). It is the page's headline Abstract — reading it alone should suffice to understand the model; never ship a terse summary in its place.
4. **Every class needs `ex:component`.** Choose components along bounded-context / cohesion lines. The diagram clusters by component.
5. Mark value objects with `ex:valueObject "true"`.
6. For DMN, emit `{"decisions": [...]}` in `<script id="model-dmn">`. For Horn rules, one clause per line in `<script id="model-horn">`. Skip these scripts entirely when not requested.
7. Don't edit the inline `<script>` containing the runtime; it is what produces the diagram, ontology, syntax, and summary.
8. Validate with `scripts/validate_model.py` until it reports no failures (exit 0).
