nine skills, ten stage rows

Each skill has one job, stated in its own words.

Eight of the nine ship in this package; every card below is condensed from that skill's own SKILL.md description, with nothing added. /domain-forge covers two rows of the chain map — it forges a model from prose and it refines any model — which is why ten stages are nine skills.

noctua /noctua

The orchestrator, above the grid rather than in it, because it is not a stage. It reads a project, classifies its sources, reads the ledger, and drives the right lane stage by stage by invoking the specialist skills, verifying each product before proposing the next. It never does a stage's work — not a little of it, not the easy part.

/noctua <path> --goal <stage> --unattended status --lane <name>

spec-analysis

/spec-analysis

Analyze an existing software project, a data project or a database, and explain it back as a read-only HTML report: components and responsibilities, behaviours and business rules, decision logic, the data model and the flows, as connected prose — reading the code but never modifying it.

codebase / data code / schema→spec-analysis.html

source: spec-analysis

domain-forge

/domain-forge

Turn a textual project idea into a visual, language-agnostic domain model in one self-contained HTML file: entities and relationships extracted from prose, made compatible with ontology T-box/A-box, DMN decision tables and Prolog/Horn rules. It owns the model platform — the contract, the engines, the validator and the layer tools.

prose, or any model to refine→<stem>.domain.html

source: domain-forge

dataset-forge

/dataset-forge

Geometric, neurosymbolic analysis of a tabular dataset: its dimensions, its basis — the minimal set of mutually non-derivable features, every other column expressed as a derivation rule — the dependencies among basis members, and the feature/label partitions they imply, modelled so the engines verify what the model proposes.

dataset→<stem>.domain.html + geometry

source: dataset-forge

data-lens

/data-lens

Traditional, best-practice analysis on top of that geometry: quality and missingness mechanisms, distributions and outliers, inference with assumption checks and effect sizes, importance and leakage probes, time series, spatial structure, drift. An observation is a finding only if it changes a downstream decision.

dataset model (+ dataset)→<stem>.analysis.html + analysis

source: data-lens

dataset-shaper

/dataset-shaper

Materialize decisions the analysis already took: compile a declarative, provenance-traced recipe of transformations, execute it deterministically, verify it, and emit the shaped dataset, a manifest, a lineage, a standalone reproduction script and an additive shape layer.

model with geometry (+ analysis)→<stem>.shaped.html + shaped/

source: dataset-shaper

inferred-questions

/inferred-questions

Surface the latent modelling questions in a model — gaps in DMN coverage, edges of OWL restrictions, SWRL antecedents that never bind, multi-typing under disjointness, rationale that names an external system without defining its failure mode. The input file is never modified.

any model→<stem>.questions.html

source: inferred-questions

model-chat

/model-chat

Hold an engine-grounded conversation with a model. Every answer is produced by running the model's own engines — SPARQL, the RDFS/SWRL reasoner, Prolog, DMN — never by LLM speculation; when no engine can ground a question, the skill refuses and names the gap.

any model→<stem>.chat.html

source: model-chat

blueprint

/blueprint

First-architecture proposal for a greenfield project: ingest a spec-analysis HTML or a model, derive a proposed architectural style and world model plus ranked design findings, every claim traced to the spec or stamped as a designer's choice. With a dataset model it proposes the pipeline the geometry, analysis and recipe imply.

prose spec or model→blueprint-runs/<ts>/

source: blueprint

/document-project external

Not part of this package, and described here only by its row in the chain map: it is the last stage of every lane, it consumes everything above it, it produces LaTeX and a PDF chapter by chapter, and the check the orchestrator runs on it is that the PDF compiles.

how it verifies

The engines decide, and the numbers are published.

A chain of language-model outputs is only worth as much as the checks between its links. These are the checks, and below them the results of the v3 build — including what it did not cover.

One file, no network

The artifact is one self-contained HTML file with no network dependencies, and the SPARQL, SWRL, Prolog and DMN engines that answer questions about it travel inside it. Open it in a browser five years from now and it still runs.

Every step is reversible

Each chain skill is a pure function over that file: the input is never modified, the output is a strict superset, and stripping a layer returns the predecessor byte for byte — strip(apply(x)) == x. To revert a step you open the previous file.

Determinism is tested, not declared

The standalone pandas script the shaper emits is a second implementation of the same recipe. Its outputs have to match the manifest's digests byte for byte, and they do — that is the test, not a promise in a README.

The validator, not the author

validate_model.py checks invariants 1–19, of which 13–16 are the layer-chain invariants that hold the superset property. The orchestrator runs a stage's own check before the lane is allowed to advance; a product that failed never becomes the current artifact.

State on disk, not in a conversation

.claude/noctua-ledger.md holds the chain state — sources with their digests, lanes, objectives, history. It is deliberately separate from the forges' .claude/domain-forge-memory.md, which records modelling decisions; Noctua reads that file and never writes to it.

What those numbers do not cover

  • The two validator warnings were rdflib and a headless browser missing from that sandbox, not defects in the model.
  • B7 — the run on the real CIC-IDS2017 folder — was not executed, because the dataset was not reachable from that session. The equivalent ran on a synthetic folder of the same shape.
  • One failing case, PSI against permutation, turned out to be a wrong test rather than a wrong check; it is documented as a limit in shape-contract.md §3 instead of being quietly removed.
  • One static verifier, dataset-shaper, returned REVISE on its first pass and SHIP on the second. The first pass counts.

get started

Nine folders, a Python environment, one command.

Install the folders

Copy the package's nine skill folders into your Claude Code skills directory, in place of the v2 ones. effective-java stays as it is — it is blueprint's anchor corpus, an external skill this package does not carry.

domain-forgedataset-forgemodel-chat inferred-questionsspec-analysisblueprint noctuadata-lensdataset-shaper effective-java

Have the environment

Python 3.10 or later with rdflib, numpy, pandas, scipy and scikit-learn; pyarrow for parquet, statsmodels for time series, geopandas, pyproj and shapely for spatial work; matplotlib for figures; and a headless Chromium or Chrome on PATH or in $CHROME for the symbolic verification and the smoke tests.

Run the owl

/noctua

On a first run it creates .claude/noctua-ledger.md and says so, checks the environment and reports which lanes that leaves open, classifies the sources it finds, asks once per lane what the lane is for — offering destinations with what each one does not give you — then proposes the next stage with the exact invocation, and waits.

specified, not built

Four chain skills are still sketches.

The design contract names them and marks their status as sketch. They are listed here with that word, because a roadmap presented as a feature list is the oldest lie on a project page.

/architect and /improve are built and installed, but Noctua never schedules them on its own initiative: it names them as options when their input exists.
